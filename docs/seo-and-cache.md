# 공개 페이지 SEO와 백엔드 부하

## 캐시 정책

| 대상 | 동작 |
| --- | --- |
| 공개 뉴스레터 목록·상세 API | Next.js Data Cache에 60초 재검증 간격을 둬 짧은 시간의 반복 조회를 줄인다. 목록은 랜딩·디렉터리·사이트맵에서 공유한다. |
| `/`, `/newsletters`, `/newsletters/[id]`, `/sitemap.xml` | 공개 조회의 `next.revalidate`를 따라 HTML/XML을 재사용한다. 페이지마다 별도 TTL을 두지 않는다. |
| 같은 렌더의 메타데이터·본문 | React `cache()`로 Promise와 오류를 공유해 중복 호출을 피한다. |
| 브라우저의 공개 목록·상세 | 서버 초기 데이터를 사용하며, 기존 QueryProvider의 `staleTime` 60초를 따른다. 별도 1시간 정책과 창 포커스 자동 재요청은 사용하지 않는다. |
| 내일 발행 목록 | 분 단위 polling을 제거했다. 한국 자정이나 날짜가 바뀐 후 탭 복귀 시 발행 요일을 갱신한다. |
| 회원 구독·읽음·개인화 데이터 | 공개 서버 캐시에 저장하지 않는다. 기존 회원 API와 별도 쿼리 키를 사용한다. |

60초는 동시·반복 요청을 줄이기 위한 시작값이며, 데이터가 반드시 60초 안에 갱신된다는 보장은 아니다. 만료 뒤 방문이 있을 때 재생성하고, 장애 시 성공했던 페이지 캐시를 유지한다. 브라우저에서 계속 열린 화면을 주기적으로 갱신하지는 않는다. 서버 조회 실패를 빈 목록이나 빈 상세로 바꾸어 정상 응답으로 캐시하지 않는다.

고정 1시간을 여러 곳에 복제하지 않고 서버 공개 조회 한 곳에서 간격을 관리한다. 사용되지 않는 캐시 태그나 별도 캐시 저장소·갱신 API는 두지 않는다. 실제 요청량과 갱신 지연을 관찰한 뒤 이 값을 조정한다.

서버 전용 데이터 진입점은 `src/entities/newsletter/api/public-newsletter.server.ts`다. 공개 조회만 이 모듈로 연결한다. 회원 응답, 액세스 토큰, 요청 헤더를 이 캐시에 넣으면 안 된다.

## 크롤링 범위와 초기 요청

- 기본 공개 경로와 뉴스레터 상세만 사이트맵에 넣고, 상세 canonical은 해당 상세 URL을 가리킨다.
- 검색·개인 화면과 `/newsletters`의 쿼리 문자열 변형은 robots.txt에서 수집을 제한한다.
- API 경로는 수집을 제한하되 `/api/backend/public/` 이미지 경로는 허용한다. JS·CSS·폰트는 차단하지 않는다.
- 랜딩·공개 디렉터리는 첫 HTML에 실제 뉴스레터 링크를 제공한다. 디렉터리의 필터 UI가 준비되기 전에도 같은 초기 목록을 표시한다.
- 뉴스레터 카드와 상세의 아티클 링크는 자동 prefetch를 끈다. 화면에 노출된 카드 수만큼 미리 상세 API를 호출하지 않는다.
- 빌드 시 인기 뉴스레터 12개만 미리 생성하고 나머지는 첫 방문 때 생성한다. 형식이 잘못된 ID는 API 호출 전에 404로 처리한다. 유효한 숫자 ID의 존재 여부는 상세 API 응답으로 판단한다. 목록 캐시에 아직 없는 신규 뉴스레터도 직접 링크로 열 수 있다.
- 상세 존재 여부가 결정되기 전에 `200` 응답을 내보내지 않도록 뉴스레터 경로의 `loading.tsx` 스트리밍 경계를 제거했다. 클라이언트 데이터 로딩 UI와 디렉터리 초기 목록은 유지한다.

`robots.txt`는 이를 준수하는 크롤러의 수집량을 줄이는 규칙이다. 이를 무시하는 봇이나 직접 API 요청을 제한하는 방화벽은 아니다. 그런 트래픽이 관측되면 배포 플랫폼/백엔드에서 경로별 rate limit과 봇 방어를 별도로 적용해야 한다.

운영에서는 `NEXT_PUBLIC_SITE_URL`을 대표 도메인으로, `ALLOW_INDEXING=true`로 설정한다. 개발·미리보기 배포에서는 검색 수집을 허용하지 않는다.

## 검증

격리된 Next.js 프로덕션 서버와 요청 횟수를 기록하는 테스트 API로 확인했다.

- 캐시된 랜딩·디렉터리·상세·사이트맵·필터 URL 17회 요청: 백엔드 추가 호출 0회.
- 아직 생성하지 않은 유효한 상세 URL 동시 요청 5회: 상세 API 호출 1회.
- 목록 캐시에 없는 신규 뉴스레터도 상세 API에 존재하면 HTTP 200.
- 없는 숫자 ID는 상세 API의 HTTP 404를 반영한다. 잘못된 형식의 ID는 백엔드 호출 없이 HTTP 404.
- 404 응답 이후 해당 ID를 등록하면 60초 캐시 만료 뒤 요청으로 재검증하고 HTTP 200으로 전환된다. 테스트에서는 첫 만료 요청이 기존 404를 반환하고, 재검증 완료 후 다음 요청이 200을 반환했다.
- 프로덕션 빌드 결과에서 랜딩·디렉터리·상세·사이트맵 모두 공개 조회의 60초 재검증 간격을 상속하는 것을 확인했다.
- ETag 조건부 요청: HTTP 304.
- 백엔드 장애: 빈 `200` 페이지로 캐시하지 않고, 백엔드 복구 후 정상 응답.
- 초기 HTML의 뉴스레터 링크, 상세 canonical·단일 브랜드 제목, robots 규칙 확인.
- 컴포넌트 검사에서 랜딩·비회원 상세·기본 디렉터리 초기 API 호출 0회, 한국 자정에 다음 요일 조회 1회, 필터 URL은 해당 필터 데이터 조회 확인.

이 수치는 해당 테스트의 캐시가 유지되는 조건에서 측정했다. 배포 환경의 캐시 제거·지역·재검증·실패 상황에서는 호출 횟수가 달라질 수 있다.
